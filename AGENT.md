# AGENT.md — how we keep brain-drain consistent

The rules for anyone (agent or person) who changes this repository: decisions, generated files, checks, git, versions and
documentation. Adapted from the datawatch project's AGENT.md for a mixed hardware / firmware / mechanical project.

- What the project is, the design and where things live: [BRAIN-DRAIN-CONTEXT.md](BRAIN-DRAIN-CONTEXT.md).
- Local Claude Code details (session markers, RTK, environments): [CLAUDE.md](CLAUDE.md).

---

## Pre-execution rule

Before acting on any prompt that changes the design, code, enclosure or docs:

0. Read `BRAIN-DRAIN-CONTEXT.md` if this is a new session.
1. Re-read the rules here that apply (decisions, generated files, testing, docs).
2. Check the planned approach follows them.
3. If the prompt conflicts with a rule, say so before proceeding.

Long sessions compress context; this is how rules survive that.

## Decisions belong to the owner

- **The project owner makes every decision** that picks between alternatives:
  parts, tools to install, topologies, board size, licences, what to build next.
- Present the options **one question at a time, interview style**, each with a
  recommendation and a one-line reason, and wait for the answer.
- Routine execution (running generators, fixing a typo, re-rendering) needs no
  question. Anything that would be argued about in a design review does.
- Record every closed decision in `docs/DECISIONS.md` with a `C<n>` number, the
  choice, the reason and the date. Open ones are `D<n>`. **Numbers are never
  reused**, even after a decision is superseded.

## Scope and safety

- Work only inside this repository. Do not install system packages, change
  system configuration, or touch other repositories without confirmation.
- Never run the sanitizer against a real disk without the safety fence
  (`software/braindrain/devices.py::classify`) and never weaken the fence.
  Any change to `devices.py` or `sim/udev.py` gets an explicit review note in
  the commit message.
- Destructive bench commands (`braindrain bench --destructive`) require the
  drive's serial number typed back; do not add a bypass.
- Vendor datasheets marked confidential stay in the gitignored
  `hardware/ref/datasheets/`; only pin tables derived from them are committed.

## Source of truth and generated files

- **One source per artefact**: `hardware/tools/design.py` for the netlist,
  `hardware/ref/*.csv` for pin tables, `enclosure/params.scad` for the shell,
  `docs/DECISIONS.md` for decisions.
- Generated files (`hardware/*.kicad_sch`, `hardware/sheets/`,
  `hardware/brain-drain.kicad_pcb` and `hardware/bay-card/*` placement and routing, `hardware/CONNECTIONS.md`,
  `hardware/bom/*.csv` and the tables in `docs/BOM.md` (`gen_bom.py`), `hardware/review/` (`make_review_pack.py`),
  `enclosure/board.scad`, `enclosure/logo.scad`, `docs/img/*.svg` from `docs/tools/diagrams.py`, `docs/img/renders/`
  from `enclosure/tools/gallery.py`) are
  **never hand-edited**. Change the source and regenerate. Hand placement on the
  board goes into `hardware/tools/placement.json`.
- Every pin in a symbol comes from a datasheet table saved in `hardware/ref/`
  with its source noted; no pin numbers from memory.
- A footprint is either from the stock KiCad library, generated by
  `hardware/tools/fpgen.py` from a vendor drawing, or copied from a vendor /
  Raspberry Pi design file with attribution in `hardware/lib/brain-drain.pretty/README.md`.
  Placeholders are labelled `PLACEHOLDER` and listed in `docs/STATUS.md`.

## Code quality

- `software/`: `ruff check` clean and `pytest` green before every commit.
  Tests exercise real behaviour (sparse-file drives, fake subprocess output),
  not skeletons. New engine paths get an end-to-end test in
  `tests/test_engine_sim.py` or `tests/test_m2_bay.py`.
- `hardware/`: `gen_sch.py` must report **0 ERC errors** for both projects; new warnings are
  explained in the commit message. `gen_pcb.py` output must load in
  `kicad-cli pcb drc` without parse errors; a routed board keeps **0 DRC errors and 0 open connections**, and `check_place.py`
  reports 0 problems. Silkscreen and branding changes must not add DRC warnings (compare the counts).
  Board edits with pcbnew run in a fresh process each (the Python proxies go stale after `Remove()` or `LoadBoard`).
- `enclosure/`: `make` must export every STL without OpenSCAD warnings; `python3 tools/check_fit.py` must report OK
  (card retention clearances) after any change to the comb, the supports or the slot positions.

## Testing tracker

`docs/testing-tracker.md` records two levels for every interface and part:

- **Tested = yes**: automated tests or generators pass (pytest, ERC, DRC, STL export).
- **Validated = yes**: confirmed on real hardware or a real drive, with the date,
  the hardware used and what was observed. Simulation never sets Validated.

Do not claim Validated from a datasheet or a simulation.

## Git discipline

- One logical change per commit, conventional message `type(scope): summary`
  with types `feat`, `fix`, `docs`, `chore`, `refactor`, `test`, `hw`, `mech`.
- Commit often; do not squash history; never force-push `main`.
- Regenerated files ship in the same commit as the source change that caused them.
- Deterministic generation: the generators use sequence-based UUIDs so a
  regenerate with no design change produces no diff.

## Versioning

- Software: semantic version in `software/pyproject.toml` **and**
  `software/braindrain/__init__.py`; both change together. Certificate
  `schema_version` bumps whenever the certificate JSON layout changes.
- Hardware: board revision `REV` in `hardware/tools/branding.py` (printed on the silkscreen and set in the KiCad title block)
  bumps on any change that alters copper or the outline; both boards share it.
- Enclosure: `version` comment at the top of `enclosure/params.scad`.
- A GitHub **release** (only when the owner says "release") attaches: the
  schematic PDF, board PDF, gerbers, STLs and the certificate schema, and its
  notes cover everything since the previous release tag.

## Dependencies

- New Python dependencies are noted in `CHANGELOG.md`; prefer the standard
  library. Hardware-only deps stay in the `hw` extra so the simulator runs anywhere.
- Before a release, `pip list --outdated` in the venv; upgrade only versions
  older than 72 hours unless the owner asks or it is a security fix.

## Planning

Work larger than a single sitting gets a plan in `docs/plans/YYYY-MM-DD-<slug>.md`
with date, scope, phases and a status line per phase, updated as work lands.

## Documentation checklist (every change)

1. `CHANGELOG.md` under `[Unreleased]`.
2. `docs/STATUS.md` if the state of any workstream or the remaining-work list changed.
3. `docs/DECISIONS.md` for any decision closed or opened.
4. `docs/testing-tracker.md` for any new interface, part or changed contract.
5. `README.md` only for user-visible changes (a new command, a new workstream, a new image).
6. `docs/README.md` index for any new document.
7. Regenerate the BOM (`hardware/tools/gen_bom.py`, never hand-edit `docs/BOM.md` tables or `hardware/bom/*.csv`) for any part change.
8. Regenerate `hardware/CONNECTIONS.md`, `docs/img/*`, the board renders (`hardware/tools/render_board.sh`, both projects),
   the case and unit renders (`make -C enclosure renders`) and `hardware/review/` that the change affects.
9. `docs/LAYOUT-REVIEW.md` and `docs/RENDERS.md` when the review items or the image set change.

## Project tracking

`docs/STATUS.md` is the single list of what is done, what is placeholder, what
is blocked on external input and what comes next. Items carry stable ids
(`R<n>` remaining, `B<n>` blocked); numbers are never reused.
